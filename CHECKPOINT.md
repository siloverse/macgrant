# CHECKPOINT — macgrant local platform

_Last updated: 2026-08-20. This document is the arbiter: if Claude asserts something about this repo that isn't here or visible in the code, call it — that's drift._

**Goal:** one-VM local platform (Vagrant + Puppet + Traefik + Keycloak + observability stack) hosting the siloverse learning apps. Design constraint: exactly one machine, YAGNI throughout — this exists to learn DDD, event-driven architecture, distributed microservices/observability/CI-CD on a laptop.

## Locked decisions

- **No IP addresses in app repos (2026-08-19).** Silos keep Spring's default bind (all interfaces) and declare only their port. macgrant owns the network facts: `macgrant::domain/vm_ip/host_ip` in `data/vagrant.yaml` are the single source of truth — hiera interpolates them (`%{lookup(...)}`), the Vagrantfile reads the same file for the VM network, cert preflight, and DNS trigger. Rationale: config that varies by environment lives in the environment; the repo that owns the environment owns its facts.
- **Host split DNS is persistent config, not runtime state (2026-08-19).** `/etc/systemd/resolved.conf.d/macgrant.conf` routes `~macgrant-platform.test` → 192.168.56.10. The `resolvectl` trigger script kept dying on host reboot (runtime-only) and couldn't sudo from Vagrant triggers; the drop-in survives reboots. Trigger script retained as a harmless re-apply.
- **Committed dev credentials tolerated in `data/common.yaml`** (header says why: disposable local VM). The silo client secret that leaked into pushed silo-repo history is treated as **burned** — remedy is rotation (fresh secrets minted for realm `kyc`), never history rewrite on published branches.
- **Keycloak version pinned** (`profile::keycloak::version` in versions.yaml) like every other component; previously floated on the module default.
- **Realm `kyc` roles are declared as the complete list** (`manage_roles` semantics): `['user','admin']`. Consequence, chosen deliberately (YAGNI): Keycloak's built-in realm roles `offline_access` and `uma_authorization` are **removed**. Re-add `offline_access` if refresh-token/offline flows ever appear.
- **Identity model lives in its own profile** (`profile::keycloak_realm`), separate from the server (`profile::keycloak`): they change for different reasons and at different speeds. Ordering edge `Class['profile::keycloak'] -> Class['profile::keycloak_realm']` because the realm provider shells out to kcadm against a running server.
- **Confidential silo clients are deny-by-default**: only `service_accounts_enabled` (client_credentials) is on; standard/implicit/direct-access flows off. A client = an identity plus an explicit list of ways it may obtain tokens; every disabled flow is an attack path that doesn't exist.
- **Schema-per-silo in one shared `siloverse` database (2026-08-21, Awais's call after full pressure-test; Keycloak keeps its own db).** Trade-offs were litigated: database-per-service makes the boundary physics (cross-DB joins impossible), schemas make it revocable grants — Awais chose schemas with eyes open. Standing rule that keeps the choice safe: **no cross-schema grants, ever** — a `GRANT USAGE` between silo schemas is an architecture violation, not a convenience. Setup: each schema OWNED by its silo role (schemas are closed by default → owner-only), `PUBLIC` CONNECT/TEMP revoked, `public` schema DROPPED (no shared surface), per-role pinned `search_path` (apps and Flyway need zero schema config). Old per-service databases dropped.
- **Naming convention (2026-08-21):** hyphen = platform identity (repos, Keycloak clients, Traefik hosts, **DB login roles**: `user-silo`); underscore = SQL structural identifiers (databases, schemas: `user_silo`). Cost accepted: raw SQL must quote the role (`ALTER ROLE "user-silo"`); module resources quote internally.
- **Isolation verified at two layers (2026-08-21), with an honest nuance:** wrong-schema read → `permission denied for schema` (grants layer ✓). Wrong-database connect → denied by missing CONNECT privilege, NOT by pg_hba — the puppetlabs module's `ip_mask_allow_all_users` emits a default `host all all` line that matches before our per-pair acls, so the per-pair hba lines are documentation, the grant layer is the operative wall. Accepted (YAGNI locally).
- **auth-silo SA admin grants = `manage-users` + `view-realm` (2026-08-21), least privilege learned by 403:** `manage-users` covers user CRUD and writing role mappings but NOT reading the realm role catalog (`GET /roles/{name}` for name→id) — that needs `view-realm`. The exec's `unless` keys on the newest grant so additions re-trigger idempotently. Reminder that bit: a wallet-cached token minted before a grant keeps the old claims until expiry/restart.
- **Role model = ubiquitous language (2026-08-20, Awais's design):** realm roles are `customer` (registered humans, assigned at registration in Phase 3), `employee` (operational humans), `system` (machines — every silo service account gets it via `keycloak_role_mapping`, making Phase 4's "services only" checks a clean `hasRole('system')` instead of azp sniffing). Convention (revised 2026-08-20): role names lowercase in Keycloak (`customer`), UPPERCASED by each silo's converter — Spring sees `ROLE_CUSTOMER`, checks read `hasRole('CUSTOMER')`. Chosen after the three converter copies drifted on exactly this within one day (notification-silo's test caught it) — the first concrete cost of rule-of-three copying, and the argument 8.6 will cite. Placeholder `user`/`admin` roles deleted by the declarative list. Note: `keycloak_role_mapping` is also complete-list — SAs no longer hold `default-roles-kyc`.
- **Vendor defaults stay unless dangerous (2026-08-20):** default-roles composite, account client roles, unused scope catalog are inert because authorization is allowlist-based — junk authorities grant nothing no rule names. Removing vendor state is a permanent enforcement commitment (and the module lacks types for it) — YAGNI cuts both ways: don't build speculatively, don't delete speculatively.
- **Realm `kyc` rebuilt from nothing (2026-08-20) — the IaC completion certificate.** Discovery: the realm predated the code (created manually ~Aug 4; explains the adopted hand-made auth-silo client, the drift user `macheema` with Awais's real email, and why the first provision showed property changes instead of ensure:created). Deleted realm via kcadm, one provision recreated everything: realm+roles, 4 clients, secrets, SA role mappings, test user, manage-users grant. New realm = new RSA keys; resource servers recovered via automatic JWKS refetch on unknown kid. Standing rule: test fixtures use synthetic identities (`test_user@macgrant-platform.test`), never real emails.

### Phase 1 lessons (Reflect answers, 2026-08-19/20)

- **Claims are mapper output, not facts.** Clients start with NO scopes under the treydock provider (declarative completeness) → near-naked tokens (`scope: ""`, no roles claim). Claims appear only when a client scope's protocol mappers put them there.
- **Service vs user token, field by field:** `sub` = SA-user UUID vs person UUID; `azp` = the client (auth-silo vs web-cli — tool, not identity); profile claims exist only for humans AND only with profile/email scopes; `sid` only for user logins (SSO session); `aud: account` appeared on the SA token via the roles scope's audience-resolve mapper (composite default role → account client roles), absent on the user token (import set exactly `realmRoles: ["user"]`, no default composite).
- **`scope` claim ≠ assigned scopes:** `basic`/`roles` have include-in-token-scope OFF (mapper bundles, not OAuth scopes); `profile email` show up because theirs is ON.
- **OIDC standard claims are flat and top-level** (interop); `realm_access`/`resource_access` are Keycloak-specific nesting — the exact reason Phase 2 needs a hand-written JwtAuthenticationConverter.
- **`partial_import` with SKIP is create-only** — it does not converge drift (unlike the realm/client types). Paid for it: user created without firstName/lastName → password grant refused with `invalid_grant: Account is not fully set up` (direct grant has no UI for required actions; KC 26 user profile requires first/last name). Fix required deleting the user and re-importing.
- **Signing (final Reflect, answered 2026-08-20):** realm `kyc` holds an RSA key pair; tokens are RS256-signed with the private key (never leaves Keycloak). Verifiers fetch the PUBLIC halves from `jwks_uri` (verified: `has_private_parts: false`; token header `kid` matches the JWKS `sig` key). Public key can verify but not forge — that's why the JWKS is safely public, why resource servers validate tokens locally without calling Keycloak (only an unknown `kid` after rotation triggers a refetch), and why asymmetric beats HS256 with multiple verifiers (a shared secret would let any silo mint identities). Same asymmetry as mkcert: signer keeps the private key, verifiers get the public one.

## Parked

- ~~dnsmasq leaked VM-internal loopback answers to the host~~ **RESOLVED 2026-08-20**: bit during Phase 1.5 exactly as predicted (host psql → `postgres.… (127.0.0.1)` connection refused). Fixed with `no-hosts` in dnsmasq.conf.epp — dnsmasq stops serving /etc/hosts over the network; VM-internal processes still resolve those names via nsswitch `files` (loopback, bypassing Traefik). Two resolution worlds, cleanly separated: inside = hosts file, outside = wildcard. Remember `resolvectl flush-caches` on the host after DNS-behavior changes.
- Grafana placeholder `admin_password` + `secret_key` in common.yaml (plan task 8.4).
- **Puppet quoted strings absorb line breaks (2026-08-20, cost: lost manage-users grant + a failing exec for days).** Wrapping an exec `command`/`unless` across lines for readability embedded a literal newline → the shell ran it as a two-line script (`sh: 2: --uusername: not found`). The broken `unless` always failed → exec always attempted → always errored, so the self-healing grant re-add was down exactly when a client recreation discarded the SA's grants. Fix: build wrapped commands with `join([...], ' ')` (the keycloak module's own idiom). Rule: exec commands are single logical lines; readability wrapping goes through join, never a bare quoted-string line break. (`keycloak_role_mapping` was suspected of stripping client roles — acquitted by the two-provision experiment.)
- **`partial_import` fires on file-content change, not on state** (module wires file→notify→exec). After any future realm rebuild with UNCHANGED import content, the test user will silently not be recreated — re-touch the content or run the import by hand. (This rebuild was safe only because the content changed anyway.)
- siloverse-build: `io.spring.dependency-management` in the spring-boot-application convention breaks Gradle's configuration cache (pom.withXml captures Project) and is redundant — the platform already imports the Boot BOM. Fix = delete it, bump 1.10.1.
- Vagrantfile literals `config.vm.hostname` and cert-preflight paths could derive from `macgrant::domain`; left as-is (YAGNI — revisit only if the domain ever changes).
- ~~`created secret` fired every provision~~ **RESOLVED 2026-08-20 — manual drift, not a module bug.** A hand-made `auth-silo` client predated the Puppet code; Puppet adopted it by clientId, but it carried a console-set `name` field. The treydock provider skips reading secrets for clients WITH a `name` (heuristic for Keycloak's built-in clients, whose names look like `${client_*}`) → secret never read → current=absent → same value re-PUT every run. Proof: the three purely module-created clients had no name key and were idempotent all along. Fix: deleted the drifted client(s), Puppet recreated from code; second provision = zero notices. Standing rules: (a) console clicks are drift — inspect in the console, change only in code; (b) never fill a client's Name field — a named client becomes secret-unreadable to the provider; (c) recreate a client only while its service account holds no grants (deletion discards the SA user and its roles; grants are code anyway, so a provision restores them).
